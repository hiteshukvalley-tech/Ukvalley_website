# Ukvalley Technologies — website + admin panel

Next.js 16 (App Router) site with a MongoDB-backed admin panel at `/admin`.

## Local development

```bash
npm install
cp .env.example .env.local   # fill in the values
npm run dev                  # http://localhost:3000
```

`npm run dev` compiles each page the first time it is opened, so the first
visit to a page is slow. To judge real speed, use a production build:
`npm run build && npm start`.

## Deploy to Render

The service is defined in `render.yaml` (a Render Blueprint): a Node web
service that runs `npm ci && npm run build`, then `npm start`.

1. **Push the code to GitHub.** `.gitignore` already keeps out `.env*` (except
   `.env.example`), `.next`, `.next-test`, `.shots`, `*.zip` and the local
   HTTPS certificates.
2. **Create the service:** Render dashboard → **New → Blueprint** → connect
   the `Ukvalley_website` repository → Render reads `render.yaml`.
3. **Fill in the secrets** Render asks for:

   | Key | Value |
   |---|---|
   | `ADMIN_EMAIL` | owner login email |
   | `ADMIN_PASSWORD` | a long, unique passphrase |
   | `MONGODB_URI` | Atlas connection string |

   `AUTH_SECRET` is generated by Render; `MONGODB_DB` is preset to `ukvalley`
   and `NODE_VERSION` to 22. Change any of them later under the service's
   **Environment** tab; saving triggers a redeploy.
4. **MongoDB Atlas → Network Access:** allow the service's outbound IPs
   (Render service → **Connect → Outbound**), or `0.0.0.0/0`.
5. **Deploy** (automatic on every push to `main`), then open
   `/admin/login`, sign in as the owner and check *Admin → Dashboard* shows
   "Database: Connected". If the database is new, run
   *Admin → Migration → Import all* once.
6. **Domain:** the website and the admin panel both run on
   `https://uat.ukvalley.com` (set in `render.yaml`):

   | Variable | Value | Serves |
   |---|---|---|
   | `NEXT_PUBLIC_SITE_URL` | `https://uat.ukvalley.com` | the public website (canonical URLs, sitemap, SEO, share previews) |
   | `NEXT_PUBLIC_API_URL` | `https://uat.ukvalley.com` | the admin panel and server routes (`/admin`, `/media`, `/careers/apply`) |

   Add `uat.ukvalley.com` under the service's **Settings → Custom Domains** and
   create the DNS record Render shows (a CNAME for `uat`). The admin panel is at
   `https://uat.ukvalley.com/admin`. If the two values are ever set to different
   domains, `/admin` on the website is redirected to the backend and public
   pages opened on the backend go to the website. The values are read at build
   time: after changing them, redeploy.

### Search engines and the launch checklist

A test address (`uat.`, `staging.`, `dev.` or `test.` subdomain, `*.onrender.com`,
`localhost`) is kept out of search results: `robots.txt` is `Disallow: /`, every
page carries `noindex, nofollow` and every response an `X-Robots-Tag: noindex`
header. Only a production domain is indexable. `NEXT_PUBLIC_ALLOW_INDEXING=1`
forces indexing on, `=0` forces it off (read at build time). The admin panel
always sends `noindex`.

To launch on the production domain:

1. Set `NEXT_PUBLIC_SITE_URL` and `NEXT_PUBLIC_API_URL` to the production
   domain (e.g. `https://ukvalley.com`) in Render (and `render.yaml`).
2. Redeploy (the values are read at build time).
3. Check `/robots.txt` shows `Allow: /` and the production `Sitemap:` line,
   `/sitemap.xml` lists production URLs, and a page's
   `<link rel="canonical">` and `<meta name="robots">` (`index, follow`) are
   right. Then submit the sitemap in Google Search Console.

### Google Tag Manager

Only the GTM container is installed in code (`src/components/site/gtm.tsx`,
`src/lib/analytics.ts`). GA4, Meta Pixel and other tags are added inside the
GTM dashboard.

- Set `NEXT_PUBLIC_GTM_ID=GTM-…` in Render, then **redeploy**: the value is
  baked in at build time. Empty (or the `GTM-XXXXXXX` placeholder) means no
  tracking; `NEXT_PUBLIC_GTM_ENABLED=false` switches it off for an environment.
- GTM loads on the public site only, never on `/admin` (its URLs carry
  applicant emails).
- dataLayer events:
  - `page_view` on every page, including client-side route changes
    (`page_location`, `page_path`, `page_title`). In GTM, fire the GA4 config
    tag on this custom event and turn off its automatic page view, or each
    first page is counted twice.
  - `utm_captured` once per page load: `utm_source`, `utm_medium`,
    `utm_campaign`, `utm_term`, `utm_content`, `gclid`, `fbclid`, `referrer`,
    `landing_page`. These come from the first-touch cookie `uk_attribution`,
    which lasts 30 days and is replaced only when a visit brings new UTM tags
    or click IDs.
  - `form_submit` (with the same attribution values):
    - Contact page and scoping popup: `form_name` `contact` or
      `scoping_popup`, plus `service`, `budget` and `delivery` (`saved`, `web3forms` or
      `email_app`).
    - Careers application: `form_name` `career_application`, `job_position`.
    - No names, emails, phone numbers or messages are ever pushed.
- Add new events with `trackEvent(name, data)` from `@/lib/analytics`.

### Web3Forms

The contact form and the scoping popup save each enquiry in *Admin → Leads*
and also email a copy through [Web3Forms](https://web3forms.com) to the inbox
that owns the access key (`src/lib/web3forms.ts`). If saving fails, Web3Forms
still delivers it; only if both fail does the visitor's email app open.

- Set `NEXT_PUBLIC_WEB3FORMS_KEY` in Render, then **redeploy** (read at build
  time). Empty means no email copies.
- Sent from the browser: Web3Forms' free plan refuses server-side requests.
  The key is public by design; it can only send to its own inbox.
- `form_submit` reports `delivery` as `saved`, `web3forms` or `email_app`.

### Platform notes

- Render runs one long-lived Node server, so the MongoDB connection pool and
  the in-memory login / contact-form rate limits are shared by every request.
  With more than one instance, each keeps its own rate-limit counters.
- Media files are stored in MongoDB (GridFS), not on Render's disk, which is
  wiped on every deploy. Uploads go one file per request, max 4 MB each.
- The free plan sleeps after 15 minutes without traffic and has 512 MB RAM;
  `render.yaml` uses the always-on Starter plan.

## QA

Run the suites against a production build that uses a scratch database:

```bash
NEXT_DIST_DIR=.next-test MONGODB_DB=ukvalley_qa npx next build
NEXT_DIST_DIR=.next-test MONGODB_DB=ukvalley_qa QA_ALLOW_LOCAL_SMTP=1 \
  SMTP_HOST=127.0.0.1 SMTP_PORT=2525 SMTP_SECURITY=none SMTP_USER=qa@example.com SMTP_PASS=qa \
  npx next start -p 3100
node scripts/qa/01-access-and-pages.mjs   # …02 … 15 (15: every text on every page is editable)
```

The SMTP_* values send every email to the suites' fake mail server on
localhost:2525, so no real email goes out. `QA_ALLOW_LOCAL_SMTP=1` lets the SMTP settings accept the suites' fake mail
server on localhost:2525. Never set it on Render: in production, SMTP hosts on
local or private addresses are refused.
